LLMs en la práctica y arquitectura moderna

Edición del 18 de noviembre de 2025

Esta edición está pensada para alguien que ya usa LLMs a diario y quiere entender cómo se están montando los sistemas serios hoy: multi-agente, protocolos estándar, y agentes de código como Codex trabajando sobre repos reales.

1. De “prompting” a diseño de sistemas evaluables

En 2023–2024 el foco estuvo en “prompt engineering”; en 2025 el juego real es diseñar sistemas que puedas medir y versionar. Un buen sistema con LLMs no se define por tener un prompt ingenioso, sino por:

  • Un conjunto claro de tareas objetivo (use cases concretos).
  • Métricas offline y tests automatizados para prompts y flujos.
  • Telemetría en producción: qué pregunta el usuario, qué falló, qué se corrigió.
  • Un ciclo de mejora continua (prompt + retrieval + herramientas), no solo tuning de modelo.

En vez de inventar el “super prompt”, lo que se está haciendo en equipos serios es algo mucho más aburrido (pero efectivo): guardar cada cambio de prompt en Git, tener un evaluation harness y automatizar comparativas entre versiones de flujo. Herramientas como suites de evaluación para RAG y agentes (por ejemplo, RAGAS o DeepEval) se usan justo para eso: romper la ilusión de que “se siente bien” y ver qué tanto mejora realmente.

Una regla útil para tu día a día: si no puedes escribir en una frase qué métrica quieres mover con ese cambio (precisión, latencia, coste, tasa de alucinación…), probablemente todavía estás “jugando” con el modelo en vez de diseñar un sistema.

Lecturas sugeridas: RAGAS: evaluación de RAG, DeepEval: evals para LLMs.

2. LangGraph y el renacimiento de los sistemas multi-agente

El concepto de “multi-agente” existe desde hace tiempo, pero en 2025 está encontrando una forma bastante concreta en producción gracias a frameworks como LangGraph. La idea clave: describir tu aplicación de IA como un grafo de estados y agentes, no como un solo “chat gigante”.

Según análisis recientes sobre LangGraph en sistemas de producción, el framework se usa para orquestar:

  • Agentes especializados (investigación, código, redacción) coordinados por un supervisor.
  • Flujos con ciclos, backtracking y condiciones explícitas, no solo cadenas lineales.
  • Memoria persistente y trazas detalladas por cada nodo del grafo.

Un patrón muy común es el Supervisor Pattern: un agente central recibe la petición, decide qué subagentes participan (p.ej. uno de investigación y otro de código) y va consolidando los resultados. Esto hace mucho más fácil depurar y poner límites claros sobre qué puede hacer cada agente, en vez de tener un único modelo “todopoderoso” que lo hace todo de forma implícita.

Para flujos tipo “investiga → prototipa código → genera documentación”, este modelo de grafo multi-agente es claramente superior a los pipelines lineales: puedes reintentar solo un nodo, cambiar un agente, o incluso enchufar otro proveedor de modelo sin reescribir toda la app.

3. MCP: el “USB-C” para conectar LLMs con tus sistemas

Otro tema muy caliente es MCP (Model Context Protocol), un estándar abierto propuesto por Anthropic que está siendo adoptado por OpenAI, Microsoft y otros proveedores. La idea es simple pero potente: en vez de crear integraciones ad-hoc entre cada modelo y cada herramienta, defines servidores MCP (para GitHub, bases de datos, APIs internas, etc.) y cualquier LLM compatible puede usarlos.

Dicho de forma muy burda: MCP intenta convertirse en el “USB-C de las apps de IA”. Un host (por ejemplo, un IDE o un cliente de chat) habla con varios servidores MCP que exponen recursos o acciones. El modelo usa ese protocolo para leer, escribir y ejecutar cosas de forma estándar, en lugar de miles de integraciones manuales.

Esto encaja muy bien con arquitecturas de microservicios: cada servicio puede exponer capacidades vía MCP, y tus agentes navegan el grafo de herramientas con un contrato claro. El punto delicado, y donde aún hay trabajo por hacer, es la seguridad: autenticación fuerte, aislamiento de contextos y defensa frente a prompt injection. No es plug-and-play; hay que diseñar permisos y límites como si fuera cualquier otra API crítica.

4. Tu stack hoy: Windsurf + Codex como “equipo” de desarrollo

Si ya estás pagando ChatGPT y usando herramientas tipo Windsurf, tiene sentido pensar en un stack concreto, no solo en “el modelo”. En 2025, Codex y otros agentes de código se están consolidando como piezas centrales del entorno de desarrollo.

Según la documentación actual de Codex y su changelog, el agente se apoya en variantes de GPT-5 optimizadas para ingeniería de software, con capacidades como:

  • Trabajar horas sobre un repo en una sandbox aislada.
  • Proponer y actualizar pull requests en GitHub.
  • Ejecutar tests y ajustar el código hasta que pasen.
  • Integrarse en terminal, IDE y flujos de CI/CD.

Windsurf, por su parte, funciona como un IDE pensado desde el principio para agentes de IA: entiende el árbol del repo, mantiene contexto de sesiones largas y se integra bien con agentes externos como Codex. Una manera práctica de combinarlos:

  • Usa Windsurf como entorno principal de edición y navegación del repo.
  • Delega en Codex tareas más grandes: refactors extensos, migraciones, generación masiva de tests.
  • Configura reglas claras: nada entra a main sin revisión humana y, si puedes, revisado por otra persona además de ti.

5. Qué podrías hacer esta semana para “subirte” a este nivel

Para aterrizar todo esto, aquí van ideas muy concretas que puedes aplicar ya mismo con tu stack:

  • Define un pequeño conjunto de evaluaciones para tu caso de uso principal (por ejemplo: responder preguntas sobre tu código o docs). Guarda los ejemplos y resultados esperados en un repo.
  • Esboza un mini-grafo con LangGraph (aunque sea en pseudo-código): usuario → supervisor → agente de búsqueda → agente de redacción.
  • Haz un experimento con MCP: conecta un servidor MCP a algo inofensivo (por ejemplo, un repositorio de documentación) y mira cómo cambia la forma de usar el modelo cuando tiene acceso directo.
  • Dedica una tarde a configurar Codex CLI sobre tu repositorio: deja que haga una limpieza de warnings, formateo y pequeños bugs, pero revisa todos los cambios antes de hacer merge.

La idea es que cada semana no solo leas sobre “lo nuevo en IA”, sino que incorpores una pieza tangible a tu propia infraestructura: un test de prompt, un grafo sencillo, un servidor MCP de prueba, un flujo automatizado con Codex… así tu sistema mejora al mismo ritmo que el ecosistema.

5. Arquitectura y patrones de software para equipos pequeños en 2025

La mayoría de los ejemplos “cool” de IA vienen de empresas gigantes, pero en la práctica muchos equipos son de 2–6 personas que necesitan entregar valor cada pocas semanas. Para ese contexto, los patrones que más están funcionando tienen en común algo simple: arquitecturas poco exóticas, bien observables y fáciles de depurar.

5.1 Monolito modular + servicios de IA bien encapsulados

Para un equipo pequeño, un monolito modular (por ejemplo, una API en Django / Rails / FastAPI / Nest) con límites de módulo claros suele ser más efectivo que un zoológico de microservicios. La IA entra como:

  • Un servicio interno de LLM que expone endpoints tipo /chat, /rag, /agent.
  • Un módulo de integración que habla con proveedores externos (OpenAI, otro vendor, modelo on-premise).
  • Adaptadores thin (muy delgados) en el monolito que llaman a ese servicio, sin lógica de negocio duplicada.

Esto permite cambiar de modelo o de proveedor sin reescribir toda la app y mantiene la lógica de negocio donde siempre debió estar: en tu código, no en el prompt.

5.2 RAG como “feature”, no como plataforma

El patrón de Retrieval-Augmented Generation (RAG) es casi obligatorio, pero para un equipo pequeño es mejor verlo como una capacidad concreta (buscar en tus docs, código, tickets) y no como una mega-plataforma.

  • Un índice vectorial sencillo (pgvector, Qdrant, Weaviate, Elasticsearch con dense vectors).
  • Uno o dos pipelines de ingestión pequeños y mantenibles (no 15 conectores medio rotos).
  • Una capa muy clara que decide qué se indexa, cuándo se refresca y cómo se trocean los documentos.

Lo importante es que puedas razonar fácilmente: “este error viene de que este doc fue indexado así y este chunk llegó al modelo”.

5.3 Servicio de orquestación de agentes

Si empiezas a usar LangGraph u otro framework multi-agente, en lugar de meter el grafo dentro del monolito, un patrón que funciona bien es tener un “orchestrator service” separado:

  • El monolito recibe la petición del usuario y valida permisos / inputs.
  • El orquestador (LangGraph, por ejemplo) ejecuta el flujo multi-agente (investigar, llamar APIs, generar código, etc.).
  • El resultado vuelve al monolito, que hace la parte “aburrida” (persistir, notificar, emitir eventos).

Esto ayuda a que los cambios en tus agentes no rompan tu API pública y te permite iterar en el grafo con más libertad.

5.4 Patrones de equipo: cómo no morir en la complejidad

A nivel de trabajo diario, algunas prácticas que están funcionando muy bien en equipos pequeños:

  • Trunk-based development con ramas cortas y revisiones frecuentes (especialmente para cambios generados por la IA).
  • Feature flags para nuevos flujos de IA: puedes habilitarlos solo para ti o para un subconjunto de usuarios.
  • Infra como código mínima (Terraform, Pulumi o plantillas CloudFormation) pero sin sobredimensionar: 2–3 módulos bien cuidados.
  • Observabilidad desde el día 1: logs de prompts, respuestas, IDs de conversación y, si puedes, métricas de calidad por flujo.

El objetivo no es montar la arquitectura perfecta, sino tener un sistema que puedas entender, que soporte iteración rápida y donde los errores sean visibles y corregibles en horas, no en semanas.
